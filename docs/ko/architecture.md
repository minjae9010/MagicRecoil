## 구현 선택

Paper 1.21.11 전용 어댑터에서 `ServerPlayer.forceSetRotation(yaw변화량, true, pitch변화량, true)`을 호출합니다. 실제 매핑된 서버 바이트코드를 확인한 결과 서버의 yaw·머리 yaw·pitch·이전 회전값을 갱신한 뒤 `ClientboundPlayerRotationPacket`을 보냅니다. 이 패킷에는 yaw, 상대 yaw 여부, pitch, 상대 pitch 여부만 있고 좌표와 텔레포트 번호가 없습니다.

서버 조준 방향도 갱신하므로 시각적 효과만 주는 패킷은 아닙니다. 이후 클라이언트가 보내는 일반 회전 패킷은 기존 서버 처리 경로를 따릅니다. 지연이 있는 환경에서는 이전 입력 패킷이 잠시 서버 추정값을 덮어쓸 수 있으며, 네트워크를 건너 양쪽 시점이 매 순간 동일하다고 보장하지 않습니다. 입력을 가로채 새로운 조준 권한 체계를 만들지 않습니다.

## 네 가지 방법 비교

| 방식 | 1.21.11 동작과 영향 | 이번 검증 범위 |
| --- | --- | --- |
| Paper `Player.setRotation` | CraftPlayer → CraftEntity에서 절대 각도를 정규화하고 상대 플래그 false로 forceSetRotation 호출. 이 버전에서는 원래부터 위치 텔레포트가 아니라 회전 전용 패킷. 계산·도착 사이의 마우스 변경을 절대 각도가 덮어쓸 수 있음 | 공식 구현과 실제 서버 패킷 확인. 절대 플래그와 즉시 서버 시점 갱신 검증 |
| 상대 회전 패킷 | 전용 패킷의 두 relative 플래그로 수신 당시 클라이언트 시점에 더함. 위치/시점 텔레포트 패킷과 구별해야 함 | 실제 로컬 프로토콜 통신 확인 |
| ProtocolLib | 같은 패킷을 감싸는 API. 클라이언트 보간 기능을 새로 만들지는 못하며 단순 송신만 하면 서버 상태 갱신도 따로 고려해야 함 | 5.4.0 실행용 all JAR로 상대 패킷 전달 확인. 즉시 서버 pitch는 0°였고 클라이언트 응답 후 -3°로 변경됨. 해당 라이브러리는 1.21.11 미검증 경고를 출력하므로 전체 호환성 보장은 아님 |
| 직접 NMS | vanilla 메서드가 서버 시점 갱신과 상대 패킷 전송을 함께 처리. 버전에 종속됨 | 실제 Paper 개발 번들로 컴파일하고 132번 서버에서 실행 |

네 항목은 서로 독립적인 전송 방식 네 개가 아닙니다. 패킷은 통신 형식이고 API·ProtocolLib·NMS는 이를 보내는 수단이므로 일부가 겹칩니다. 위치·텔레포트 확인 처리가 들어가는 position-and-look 방식은 반동 구현에서 사용하지 않습니다. 네 방식의 실측 성능 벤치마크를 완료했다고 주장하지 않습니다.

## RotateSpell과의 차이 및 한계

Beta 18 RotateSpell은 절대 각도를 읽고 변화량을 더해 Entity.setRotation을 호출합니다. Paper 1.21.11에서는 이 호출 자체가 좌표 텔레포트인 것은 아닙니다. MagicRecoil의 차이는 상대 회전, 틱 분할, 중첩 반동 병합, 연사 패턴과 중지 관리입니다. **구현 차이가 있다는 사실만으로 모든 사용자에게 체감 개선이 보장되지는 않습니다.**

회전 패킷에는 지속 시간이나 보간 곡선이 없습니다. 각 단계가 보이는 방식은 바닐라 렌더링과 도착 시간에 달려 있습니다. 서버가 초당 20번 갱신한다고 144 FPS 애니메이션을 약속할 수는 없습니다. 프레임 단위 보간은 클라이언트 모드가 필요한 대안이며, 도입 승인은 실제 사람의 RotateSpell A/B 시험을 거쳐야 합니다.

## 클래스 로딩

MagicSpells는 공개 `getClassLoaders()` 목록에서 전체 클래스명을 찾고 `(MagicConfig, String)` 공개 생성자를 요구합니다. 앞에 점이 있는 이름은 MagicSpells 내부 패키지로 확장하므로 외부 애드온은 전체 이름을 사용합니다.

plugin.yml에 `depend: [MagicSpells]`를 선언합니다. 모든 플러그인의 onLoad가 실행되는 단계에서 로더를 등록하여 MagicSpells의 onEnable 중 주문 생성에 사용할 수 있게 합니다. 주문 생성자는 설정만 읽고 아직 활성화되지 않은 관리자를 사용하지 않습니다. 리로드 때 목록이 비워지므로 loading 이벤트에서 다시 등록합니다. JAR 복사본이나 본체 패치가 필요 없습니다.

## 반동 처리 흐름

```text
기존 발사 성공 → 한 번 쓰는 성공 기록 → RecoilSpell
                                      ↓
                     검증된 설정 / 플레이어별 현재 무기 세션
                                      ↓
                         패턴 → 배율 → 한 발 크기 제한
                                      ↓
                              고정 20칸 틱 버퍼
                                      ↓
                          공용 메인 스레드 스케줄러 하나
                                      ↓
                      버전 어댑터 → 서버 시점 + 상대 회전 패킷
```

플레이어마다 현재 무기의 세션 하나만 유지합니다. 다른 반동 주문으로 바뀌면 이전 세션을 버려서 한 번 들었던 모든 총기의 상태가 계속 쌓이지 않습니다. 각 주문에는 별도 불변 설정이 있고 플레이어 사이에 연사 카운터를 공유하지 않습니다. 새 발사는 최대 20개의 미래 틱 슬롯에 더하며 스케줄러를 새로 만들지 않습니다.

첫 발 때 공용 작업을 만들고 모든 세션이 끝나면 취소합니다. 타임아웃과 잔여 반동·선택적 복귀가 끝나면 세션을 제거합니다. 세션에는 Player 객체 대신 UUID만 보관합니다. 성공 기록은 관찰 대상 주문을 호출한 플레이어마다 최대 하나이며, 같은 틱에서만 소비할 수 있고 로그아웃·초기화·리로드 시 제거합니다.

모든 Bukkit/NMS 접근은 메인 스레드에서 수행합니다. 비동기 반동 호출은 거부합니다. Netty 핸들러, 별도 타이머 스레드, 발당 스케줄러, 위치 조작, 가짜 이동 확인 응답은 없습니다. 과도한 동시 발사의 초과 반동을 장시간 뒤늦게 적용하지 않도록 틱당 45°로 제한합니다.

## 호환성 경계와 근거

1.21.11만 명시적으로 지원하며 다른 버전을 reflection으로 추측해서 실행하지 않습니다. Folia나 다른 플러그인의 회전·텔레포트 개입도 별도 검증 대상입니다. 향후 26.3 대응 시 NMS 어댑터와 MagicSpells API·로더·이벤트를 다시 검토해야 합니다.

공식 자료와 정확한 소스 기준점은 [영어 문서의 Primary evidence](../en/architecture.md#primary-evidence)에 모았습니다. 핵심 기준은 MagicSpells 커밋 `1996743cacaac8c5742ac146e7ff905caf270f8a`, 공식 Beta 18 JAR, Paper 커밋 `c5eb0790f199da6c38d0a650e1e5cd5415b28185`와 실제 개발 번들의 서버 바이트코드입니다. Java 버전은 Paper의 현재 최신 버전 설명이 아니라 1.21.11에 해당하는 표를 적용하여 21을 사용합니다.
